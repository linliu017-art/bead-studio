# 微信拼豆小游戏实施计划

状态为 M1 本地试玩完成、真机待验证。依据[开发规格 v0.2](../docs/开发规格.md)与[产品需求 v0.2](../docs/首版产品需求.md)。任务状态统一记录在 [todo.md](todo.md)，本文件不重复维护完成勾选。

## 交付策略

先让玩家完整做完草莓蛋糕，再检验小猫和橱窗，最后扩充 20 关。每一步都有可运行成果；不会先批量生产所有 UI 或图案，最后才连接玩法。

原型仅用来确认交互与视觉。正式玩法在 Cocos 中实现，核心规则和内容校验使用独立 TypeScript。已完成 Cocos 3.8.8 工程、首关本地完整试玩与微信测试包导出。双指真机与微信验证仍待账号、AppID 和设备，其他阶段尚未开始。

                         ↓
              全内容校验 → 可选图片保存 → 发布候选回归

T01～T12 完成 M1；T13～T18 完成 M2；T19～T21 与内容任务完成 M3；T22～T23 形成发布候选。图片保存是建议项，可以不阻塞核心版本；未完成时隐藏入口，不能留无效按钮。

## 模块衔接

关卡只提供目标数据；会话持有放豆和阶段真值；输入负责产生操作意图；视图读取状态进行局部更新。存档保存完整玩家记录，平台层负责实际读写与生命周期，页面层不直接操作存储。

第一关使用临时入口和最小作品预览即可验收。完整首页、关卡列表与作品集在基础流程可玩后补齐。正式版只按目录顺序解锁；开发用样本直达入口隔离存档，并从发布包移除。

内容制作可在数据格式稳定后独立进行，但最终接入和验收仍遵守依赖顺序。不预先启动额外开发会话或分派任务。

## 风险处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 尚无微信 AppID | 微信真机阶段不能通过 | 基础开发继续，账号申请同步推进 |
| 引擎固定为 3.8.8 | 命令行冷启动存在导入器时序风险 | 项目等待扩展与构建资源检查已接入，记录在 README |
| 原型与工程视觉偏差 | 用户确认的画面丢失 | 对照 approved 原型，在 C1 和 C4 留存截图 |
| 双指与放豆冲突 | 误触、跨屏连线 | T05 状态机和取消处理，尽早真机验证 |
| 大图节点与存储开销 | 连续操作卡顿 | 分离静态层、复用对象、批量刷新，M2 测量 |
| 本地存储被清理 | 无法跨设备或删除后恢复 | 首版明确本地存档范围，不宣传云恢复 |
| 图纸过碎或耗时太长 | 玩家完成动力不足 | 先用三个样本测试再扩量，保留大块与细节的节奏 |
| 内容及素材来源不清 | 无法确认使用范围 | 每张资源有来源，缺失时不进入发布包 |

## 工期与准备项

不在未创建工程、未验证工具链和手感前承诺上线日期。T01～T06 完成后，根据实际耗时估算剩余工程工作；关卡美术制作和平台办理分别计时。

待准备项为 Cocos 开发者账号、微信开发者工具、AppID、两类真机和正式名称。引擎已固定为 3.8.8。现有已确认操作页继续作为对照，其他页面在对应任务中设计和验证。

## T13 首页与继续游戏实施细化

依据 [home-routing 规格](../SPEC-home-routing.md)。保留现有单场景和 A/B 快照；先在现有加载及恢复路径接入首页，按保存状态决定继续入口，再让游戏返回前刷新待保存进度。后续 T14、T15 接入首页预留导航。使用独立测试来源进行浏览器验证，不触碰用户现有存档。

依赖顺序：状态与首页入口 → 返回与保存 → 构建及端到端验收。主要风险是返回时保存失败、异常存档被覆盖和页面切换产生重复监听；分别通过失败分支、既有恢复界面和往返回归验证。微信真机验收独立保留为待办。

# 微信拼豆小游戏开发规格

版本 v0.2 · 2026 年 10 月 18 日 · M1 本地试玩完成，微信真机待验证

本规格把已确认的拼豆玩法和操作页转成 Cocos 工程约束。第一阶段交付一关完整可玩的微信小游戏；第二阶段验证三档复杂度；第三阶段扩充至 20 关。M1 已创建实际 Cocos 工程并完成本地完整试玩；微信测试包已导出，真机尚未验证。后续阶段仍为计划，实际结果见[首关开发记录](首关开发记录.md)。

## 1 依据与范围

产品依据为[首版产品需求 v0.2](首版产品需求.md)。视觉依据为用户确认的[操作页原型](../designs/bead-game/index.html)及其 `_d_meta.json` 中 approved 记录；其他历史 HTML 不作为开发依据。

已确认的约束：

- 微信小游戏方向，个人主体，竖屏；自由创作放第二版。
- 精致像素手作，第一关有完整构图、阴影与装饰，不能降级为简单爱心或小花。
- 奶油白底色、浅暖粉棋盘、草莓红强调，保留鲜艳豆子和适度立体感。
- 去掉缩小、放大、复位、移动四个按钮，保留找一找；缩放和平移使用双指手势。
- 点击和滑动放正确色；拼完后熨烫、揭纸、收藏、解锁下一关。

本规格沿用以下首版建议：无倒计时、生命值、金币、广告和内购；本地存档；20 关、两个主题。图纸与单关时长仍需试玩验证。

当前已具备 Cocos Creator 3.8.8 工程和首关 Web / 微信测试构建。实际玩法由引擎实现，HTML 原型仅作设计依据。用户没有开发者账号，当前不涉及账号注册或上线。

## 3 技术与工程结构

固定 Cocos Creator 3.8.8、TypeScript 5.9.3、Vitest 5.0.5、tsx 4.23.15、pnpm 11.25.0；本次 Node.js 24.19.0。使用 pnpm-lock.yaml 固定依赖，避免开发过程中随意升级。

Cocos 负责场景、UI、精灵渲染、动画和触摸接入。关卡校验、落豆判定、进度、熨烫覆盖和存档结构使用不依赖 Cocos 的 TypeScript，便于独立测试。

结构如下。M1 的显示、输入、提示与弹层集中在 game/BeadGame.ts，配色在 game/Theme.ts。prefabs/ui、scripts/ui、themes 等将在后续扩展时按需建立：

```text
assets/
  scenes/Game.scene
  prefabs/ui/                 首页 关卡 作品集 设置弹层
  prefabs/game/               棋盘 豆子 熨斗 成品
  scripts/
    core/                    纯逻辑 类型与状态转换
    game/                    引擎组件 渲染与输入
    ui/                      页面和弹层
    platform/                微信与浏览器适配
  resources/
    levels/                  关卡 JSON 和目录
    art/                     图集 字体与图片
    audio/                   短音效
    themes/                  配色和尺寸参数
scripts/                     关卡检查与辅助脚本
tests/                       纯逻辑单元测试
settings/                    引擎生成的项目配置
build/                       本地构建产物 不纳入源码管理
designs/bead-game/            原型与历史版本
docs/                        产品与工程文档
tasks/                       计划与任务清单
```

M1 使用 Game 一个场景，由 BeadGame 完成初始化、资源错误重试、游戏和最小作品弹层。完整首页、关卡列表与扩展作品集留到 M2，再拆分路由和 UI 组件。此为首关范围内的工程组织调整。

## 4 模块与接口

所有模块共用 core 类型。依赖方向从纯逻辑流向表现，不允许 core 反向调用 UI、微信或引擎。

| 模块 ID | 职责 | 主要依赖 |
| --- | --- | --- |
| level-data | 读取和校验关卡，提供有效目标位置和色数 | core 类型 |
| play-session | 当前作品、正确放豆、进度、阶段转换 | level-data |
| board-view | 底板、目标提示、豆子、局部更新 | play-session 的只读状态 |
| board-input | 坐标转换、单指铺豆、双指缩放与平移 | board-view 的坐标接口、play-session |
| finishing | 熨烫覆盖、揭纸、完成展示 | play-session、board-view |
| save-progress | 读取、验证、恢复和保存整个玩家记录 | core 类型、platform 存储 |
| navigation-collection | 首页、关卡、收藏、解锁与重玩 | level-data、save-progress、play-session |
| platform | 生命周期、安全区域、音效、图片保存 | 微信或浏览器运行环境 |

建议接口职责：

- `placeBead(index, colorId)` 返回 accepted、already-filled、wrong-color、out-of-bounds 或 invalid-phase，不在失败时改变状态。
- `applyStroke(indices, colorId)` 去重后逐格判定，返回本次新增位置；数据层不能信任输入控制器已校验。
- `getColorRemaining(colorId)` 与 `getProgress()` 从当前状态计算，不能由 UI 自行累计形成第二份真值。
- `heatStroke(points, radius)` 只在熨烫阶段生效，记录经过的目标格子。
- `collectLevel(levelId)` 生成包含收藏、通关和解锁的完整候选记录；持久化成功后才提交领取成功。
- `load()` 返回 valid、empty、recoverable-backup、invalid 或 storage-error；`save(snapshot)` 明确返回成功与失败。
- UI 发送意图，控制器更新状态，渲染读取结果。引擎节点、动画对象不进入存档。

## 5 关卡与玩家数据

### 关卡格式

```ts
interface LevelDefinition {
  schemaVersion: 1;
  id: string;                 // 如 dessert-001，发布后不复用
  revision: number;           // 图纸发生变化时递增
  order: number;              // 正式关卡顺序
  title: string;
  themeId: string;
  width: number;
  height: number;
  palette: Array<{ id: number; code: string; name: string; hex: string }>;
  cells: number[];            // 按行展开，0 为空，其余引用 palette.id
  regions?: Array<{ id: string; title: string; indices: number[] }>;
}
```

第一阶段使用 28×28 草莓蛋糕，保留现有图案的 334 个有效位置、7 色作为迁移验证样本。它略高于旧稿早期 180～300 颗的建议范围，实际时长通过试玩验证，不为凑数量删掉细节。其余图纸按内容目标制作。

首版支持最大 48×48 的底板和 14 色，实际有效豆数以既有 20 关规划为目标；超过上限的内容先报校验错误，不自动缩图。

关卡检查必须拒绝：尺寸与数组长度不符、未知色号、重复 ID、非法颜色、空图、重复或不连续顺序、预览资源缺失、区域越界或重叠。配置区域时，每个有效目标格子必须恰好属于一个区域，空白格不计区域。

### 玩家记录

完整记录包含以下字段：

| 数据 | 内容 |
| --- | --- |
| 记录头 | schemaVersion、递增 revision、内容校验值、更新时间 |
| 玩家进展 | 已通关关卡 ID 集合、已收藏关卡 ID 集合、最近进入关卡 |
| 设置 | 音效开关、新手引导已完成步骤 |
| 关卡会话 | levelId、levelRevision、phase、已放位置、已熨烫位置、当前色号 |

解锁结果从已通关关卡与正式目录计算，不额外维护一份可独立失效的解锁列表。正式顺序进展须保持连续，开发样本使用独立记录空间，不通过完成第 11 或 16 关样本跳过前置关。领取后的收藏必须对应通关状态。

一个关卡最多保存一份当前制作会话；重玩覆盖该关卡的会话，既有收藏和后续解锁保留。视口缩放可以不持久化，恢复时完整展示作品。仅凭系统时间不能判断哪份记录更新，以递增 revision 为主。

运行时可用位图或集合表示已放位置，持久化必须序列化为明确的 JSON 数组。读取时验证索引范围、目标存在、数组去重、关卡版本和阶段前提。

## 6 游戏阶段和完成条件

```text
loading → placing → ready-to-iron → ironing → ready-to-reveal → collecting → collected
```

- loading 失败时停留错误页并可重试，不能显示不可操作的半张图。
- placing 中只有正确颜色能新增位置；全部目标位置完成后才进入 ready-to-iron。
- ready-to-iron 等待玩家点击，不自动跳过制作反馈。
- ironing 的有效目标覆盖全部完成后进入 ready-to-reveal。
- 玩家拖动揭纸或点击揭开后进入 collecting，揭纸动画可以被跳过。
- collecting 保存成功后进入 collected，展示已收藏并允许下一关。失败时提示重试，保留本次进度。
- collected 重复进入不会重复发奖。重玩建立新的 placing 会话，不回退玩家历史进展。

UI 的整数百分比仅作显示；完成条件使用位置集合严格比较。恢复状态为“已完成拼豆但记录仍在 placing”时可推进至 ready-to-iron；任何需要补齐未知格子才能恢复的异常都不可默默修复为完成。

只有合法状态事件能改变阶段。提示、动画回调和点击连击不能绕过阶段检查。

## 7 坐标和触摸规则

底板局部坐标以左上角为原点，向右为 x，向下为 y；数组索引为 `row * width + column`。格子边界采用左闭右开、上闭下开，最右侧和最下侧边界不属于棋盘。

屏幕坐标先通过正确的 UI 摄像机与节点变换转换到棋盘局部，再除以格子边长计算行列。禁止直接用手机物理像素除以格子边长。画布适配、安全区域和节点缩放不得造成重复换算。Cocos 的 2D UI 节点事件需要 UITransform，并分别提供开始、移动、结束、取消事件。[Cocos 节点事件说明](https://docs.cocos.com/creator/3.8/manual/zh/engine/event/event-node.html)

输入控制器至少包含 idle、placing、transforming、await-release 四种状态：

1. 所有倍率下，单指或鼠标左键拖动均连续铺豆，移动时沿路径插值。移动棋盘使用独立意图：手机双指平移，电脑右键拖动或按住空格再左键拖动，不因倍率变化切换默认铺豆行为。
2. 两个采样点之间按格子穿越算法枚举经过的格子；只在边角接触而未进入的相邻格不补放，避免对角线铺豆过宽。
3. 本次手势对同一格去重，跨手势重复触碰也不得重复计数或播落豆动画。
4. 第二根手指出现立即切换 transforming，停止放豆。此前已合法放下的豆子保留，不回滚。
5. 双指缩放以中心点为基准，同时支持移动；缩放范围为 1～3 倍，边界限制避免作品完全移出视区。
6. 双指变成单指后进入 await-release，剩余手指不能继续放豆；全部抬起后回到 idle。
7. 取消、切后台、打开弹层时清理手指缓存和上一采样点，避免恢复后的跨屏连线。
8. 引擎会在鼠标事件之前模拟触摸事件，连右键也会模拟。开始触摸暂存到鼠标按键确认或下一个调度周期；右键事件取消待放豆并启动平移。第二根手指、滚轮、弹层和取消事件清除未提交的开始位置。画面按设备提示铺豆与移图方式，按键松开不把尚未结束的平移变成铺豆。

不恢复已删除的四个工具按钮。桌面预览可保留滚轮缩放作为调试能力；正式手机交互不依赖它。找一找优先定位当前颜色的一颗未完成豆子，自动平滑放大到至少 2.4 倍、最多 3 倍，保留原有更高倍率，将目标居中；边缘位置也可以居中。目标以闪动描边和箭头持续标记，填好或换色后消失，再次点击按稳定顺序找下一颗并循环跳过已完成位置。当前色已完成时同步选择另一种未完成颜色。该操作不自动放豆、不改变完成数；完成全部拼豆后不继续提供目标。

当前颜色完成后标记完成并提示换色，不自动重排色板或强制替玩家换色。已完成颜色可选中查看，但不产生新增放豆。

桌面鼠标进入可放豆视口时，普通指针替换为粉紫双色宽柄弯头塑料镊子，按用户实物图绘制粉色上臂、紫色下臂、握持防滑纹和浅色高光，夹持当前选色的豆子。镊子和夹持豆子整体使用棋盘倍率等比例缩放，夹臂曲线在未缩放坐标中绘制，不能只撑开夹口而保持柄部大小。夹持豆子与棋盘共用精灵尺寸，显示边长为格子边长 × 0.95 × 当前倍率，不加最小或最大尺寸限制，松夹过程中也不缩小豆子。夹持豆子中心与原输入坐标重合，工具绘制在界面上层且不拦截输入；成功落豆播放短促的松夹与回夹动画。已完成颜色显示空镊子。移出视口、移图、打开弹层、切后台及结束拼豆时恢复普通光标；手机触摸不显示鼠标工具。

## 8 渲染 音效与界面

使用图集精灵复用豆子造型，根据色板着色；底板与静态孔位尽量批量绘制。采用对象复用与脏位置更新，禁止每放一颗豆重建整张棋盘或逐颗创建独立材质。

豆子分成目标提示、已放置圆环、融合后成品三类表现。未拼目标适度降低饱和度并保留可辨认色相，当前选色目标提高可见度并逐格加深色细圆环描边（包含奶油白等浅色）；仅未放位置有描边，填好或换色后对应描边消失；已放豆子保持原色和完整不透明度，提示标记不把未拼豆子显示成已完成颜色。拼豆阶段的中心孔、亮边、内壁和落影保持清楚；熨烫后的区域封闭中心孔并连成无缝色块，同色连续、异色相接，不再逐格显示孔洞或圆角边框。成品材质以用户确认的 `references/fused-finish-approved.png` 为方向：整体平整轻薄，只有细微多尺度塑料颗粒与极浅的融合压痕，不做逐颗凸起、深孔或明显豆粒边框。相邻异色色块轻微软化交界，只有作品外轮廓做柔和圆角、克制的边缘明暗和窄接触阴影，保留原图案及配色。棋盘与收藏弹层复用同一成品绘制组件。首关完成熨烫后直接使用用户确认的透明底图片 `assets/resources/art/finished-cake.png`，按作品有效格范围等比适配，保留生成图的压痕、柔和鼓边与轻微厚度；不再用轻质感像素表面重建最终成品。熨烫中的局部覆盖仍以原格子集合显示融合过程，全部覆盖后切换完整图片；已收藏作品直接显示新素材。实际颜色以原型最新 `colors` 配置为迁移起点，主题色从同一份配置读取，不散落在多个组件。

主要布局沿用确认原型：顶部导航居中显示“01关 草莓奶油蛋糕”，下方展示阶段，中间大棋盘，找一找位于棋盘右上方，以放大镜图标替代文字，使用紧凑圆角底和 44×44 的点击区域；底部为色板和进度操作。不再显示单独的章节说明、“甜品时光”导航标题、“01 手作”徽章和色板上方的重复作品状态标题。已收藏时不展示色板下方的收藏文案；底部不常驻显示自动保存提示，保存失败仍通过即时提示和设置重试处理。设计基准宽度为 390，适配内容宽度约 320～430 的竖屏设备；高度不足时优先收紧间距，不能让领取和下一关按钮超出可操作区。

棋盘右下角以“宽×高”固定显示当前底板尺寸（首关 28×28），替代缩放百分比；滚轮、双指和放大镜仍正常缩放，尺寸文字不随倍率变化。

按 2026-10-18 的尺寸参考，粉色工作区统一包住棋盘、找一找、色板和提示文字，宽度为 370 个逻辑像素，下边缘位于底部安全区上方 68 个逻辑像素。进度条与主操作按钮位于容器外，色板背景与工作区融合。最新调整同时扩大棋盘纸张和输入视口：视口宽 358，顶部位于工作区顶部下方 44，底部预留色板位置；方形底板按可用宽高取较小值适配，放豆、提示定位与熨烫共用新坐标。

首关色板使用七个抽拉式分色豆盒：外壳和顶板固定，使用低透明度白色填充、透光侧壁和斜向反光，关闭时仍可看见内部豆子；豆盘、对应豆色的大面积前板和白色把手一起滑动。未选中的抽屉默认关闭，当前选中的颜色在拼豆阶段可拉开，有余量时露出豆堆，已完成时显示空抽屉；点击已打开的抽屉将其收回，点击关闭的抽屉将其打开并选中颜色，同时收回其他抽屉，动画约 240ms。关闭当前豆盒时同时取消选色（selectedColor=null），取消棋盘选色高亮和目标描边，并隐藏夹豆镊子；未选色时禁止放豆，显示先打开豆盒选色的提示。重新打开豆盒后恢复对应选色；放大镜仍可自动选色并打开豆盒。空选色可保存与恢复，旧的数字色号存档继续兼容；普通刷新、缩放和界面重建不得自动重开已关闭抽屉。放大镜切换颜色时同步开合；该色完成后仍可选中并拉开，保留完成标记并提示换色；熨烫和收藏阶段关闭。前板保持对应豆色，边框使用同色加深，奶油白也有明确边界；选中通过拉开、较粗边框和加粗数量区分，不统一染成粉色。豆堆是库存示意，准确余量以文字为准；保留完成标记和稳定色序。快速切色从当前开合位置继续，不叠加动画；重建界面或退出时清理动画。

14 色关卡的色板改为可横向滚动的一行，保持顺序稳定、点击区域至少 44 个逻辑像素；选中色可滚动到可见位置。不得把色板压缩成 14 个微小按钮。该变化属于复杂关卡布局，M2 中验证。

落豆反馈初始目标为 100～150ms 短缩放，连续铺豆时限制音效触发频率，初始上限为每秒 12 次；音效开关立即生效。熨烫与揭纸总时长以产品稿 8～15 秒为测试目标，不设硬性等待倒计时。

首页、关卡列表、作品集需沿用已确认视觉，但当前只确认过操作页，新增页面布局属于待评审产物。

## 9 熨烫覆盖与收藏

熨烫不做热传导或刚体物理。熨斗路径在棋盘局部坐标中采样，以覆盖半径标记有效目标格。初始半径约 3 个格宽，采样间距小于半径的一半，保证快拖不会出现漏带。

已覆盖格由圆环豆精灵切换为整片融合表面中的对应区域；按覆盖集合更新显示，不因逐颗精灵留白而产生缝隙。空白区域不增加进度，在已完成区域重复拖动不增加覆盖数；不同缩放下使用棋盘局部单位计算。全部目标覆盖后才允许揭纸。

领取操作将本关通关、收藏和下一关解锁写入同一份玩家记录，使用同一 revision，保存成功后才显示领取成功。首版不发金币等奖励，所以领取只涉及作品与解锁。最后一关没有下一关入口，展示主题完成与返回作品集。

## 10 存档可靠性

存储通过 platform 适配，浏览器原型的 localStorage 不直接复用于微信运行时。

采用 A/B 两个记录槽，每份都是完整玩家快照。存档步骤为构造新快照、递增 revision、计算内容校验值、写入较旧槽、回读验证；成功后更新内存中的持久化 revision。启动时验证两个槽并选择最新有效记录，部分写入失败时仍可用另一份完整记录恢复。校验值用于发现内容损坏，不作为防作弊或身份凭证。

普通铺豆期间，脏数据每 200ms 合并保存一次，手势结束、主动返回、进入熨烫、完成熨烫、领取和切后台时立即请求保存。强制终止发生在合并窗口内时，可能丢失尚未持久化的最后约 200ms 操作；不承诺被系统突然终止时零丢失。保存失败必须提示并允许重试。

弹层打开期间不可穿透放豆。切后台后清理输入和暂停音效，回前台恢复画面，不补播历史音效。领取过程中重入或连续点击只允许一个候选保存进行。

关卡 revision 改变时，不把旧位图套到新图。保留旧记录，提示当前关需重新开始，已有收藏和其他关进度保留。损坏记录不能静默清空全局数据。

## 11 平台与内容边界

微信适配只承担当前需要的生命周期、安全区域、本地存储、短音效及可选图片保存。接口失败使用明确的可恢复状态；拒绝相册相关授权不影响制作、收藏和通关。

首版不请求手机号、通讯录或地理位置，不为进入游戏强制登录。平台正式发布如要求额外接入，先核对要求和影响，再更新工程规格。

AppID 使用项目配置，不写入业务逻辑。AppSecret、密码和身份材料不进入前端源码。平台审核资料不与游戏资源混装。

图案资源有稳定 ID、版本与来源清单。所有 20 关在打包前执行校验；资源分组以测得的包体和加载情况决定，不预设远程 CDN 或服务器。需要下载的关卡必须有加载、失败和重试界面。

## 12 编码约定

核心逻辑开启 TypeScript 严格检查。类型使用 PascalCase，函数和变量使用 camelCase，资源与关卡 ID 使用 kebab-case。函数参数与返回值明确，不在状态代码里使用 `any` 绕过校验。

```ts
type PlacementResult =
  | { kind: 'accepted'; index: number }
  | { kind: 'rejected'; reason: 'wrong-color' | 'already-filled' | 'invalid-position' };

// 只示意风格，正式函数还需处理阶段与完整输入约束。
function canPlaceAt(targetColor: number, selectedColor: number | null, isFilled: boolean): boolean {
  return targetColor > 0 && targetColor === selectedColor && !isFilled;
}
```

示例不应被当作完整实现。核心规则有单一实现，UI 不复制判定代码；引擎组件销毁时解除事件监听，重进关卡不得重复绑定。

## 13 测试和质量门槛

纯逻辑建议使用 Vitest，在初始化时固定版本。测试覆盖风险规则，不给静态配色和普通文案添加镜像测试。运行时和平台兼容性必须通过 Cocos 预览与微信真机验证。

| 层次 | 重点 |
| --- | --- |
| 数据单元测试 | 空白格、色号、关卡 revision、数组长度和异常配置 |
| 规则单元测试 | 错色拒绝、重复格去重、最后一颗判定、阶段非法转换 |
| 输入算法测试 | 坐标边界、缩放后命中、快速路径、对角线、跨边界路径 |
| 熨烫测试 | 空白区域、重复覆盖、快速跨越、最后目标格 |
| 存档测试 | 新旧槽选择、截断数据、写失败、回读失败、关卡版本不匹配、领取重试 |
| 整体人工回归 | 首次进入、完成作品、重玩、下一关、作品集、弹层和切后台恢复 |

性能为建议工程目标，需要记录具体设备与测试条件：常规操作争取 60fps，最复杂作品持续拖动不得长期低于 30fps；用户输入后 100ms 内给出可观察反馈。若达不到，先分析绘制、节点数、存储和音效开销，再调整，不能用降低图案复杂度掩盖问题。

至少使用一台 iPhone 与一台 Android 真机，覆盖完整作品和最复杂样本。测试记录写清型号、系统、微信版本、引擎版本、关卡、复现步骤和结果；未测项保持未通过，不能用浏览器结果代替。

M1 验收必须满足：正确连续放豆、无手势误连、退出恢复已提交进度、熨烫覆盖完整、领取不重复、核心流程无运行错误。M3 还需通过 20 关内容校验、14 色布局、主题收藏、最后一关和资源错误恢复。

## 14 工作边界和待确定事项

始终执行：沿用确认原型、保持核心状态单一、提交前运行相关检查、同时更新受影响规格和任务状态。

需要进一步决策：首版范围增减、换引擎、登录或云同步、收费与广告、增加外部服务、改变已确认配色。日常文件组织、复用组件和修复不需要反复确认。

不执行：提交密钥、自动注册并接受账号条款、代填身份材料、未经授权正式发布、把测试 AppID 当成发布账号、把未测项标为已通过。

不阻塞基础开发的待定项包括游戏正式名称、引擎精确补丁版、其余关卡图纸、新增页面布局和测试设备清单。微信真机预览依赖 AppID 与相应开发权限；正式上线条件由账号后台核对。
